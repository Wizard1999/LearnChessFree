# Openings explorer data

Static JSON for a left-to-right opening tree (move percentages, win/draw/loss, rating-band selector,
transpositions, opening names). Computed by us from the CC0 Lichess standard rated game dump (2026-09), so the
web app can ship it and work offline. Generated by `tools/openings/` (method, sampling, biases and validation:
`docs/openings-data.md`). Do not edit these files by hand; regenerate.

Games used: **{{GAMES_USED}}** (Blitz, Rapid, Classical only), first 16 plies of each game, sampled from {{FRAMES}}
randomly placed windows of play between {{FIRST}} and {{LAST}} UTC. Online play, not master or OTB data.

## Files

| File | What |
|---|---|
| `manifest.json` | Version, source and sampling description, the 8 rating bands (with games per band), thresholds, file names. Load this first. |
| `core.json` | `{"nodes":{id:node},"edges":[edge]}` for plies 0 to 8 (positions reached after at most 8 half-moves). |
| `chunks.json` | `{boundaryNodeId: chunkFileName}`: which chunk to load when the user expands a ply-8 node. |
| `chunks/kNNNN.json` | Same shape as `core.json`, plies 9 to 16. One chunk serves one or several boundary nodes. |

## Schema

**Node** (key = id = first 10 hex characters of `sha1(EPD)`; if two kept positions ever collide the later one gets a
longer id; none did in this build, see the doc):

```
"e":    EPD of the position (python-chess board.epd(): placement, side to move, castling, en-passant square only when a
        legal en-passant capture exists; no move counters). Two move orders to the same position give the same EPD.
"p":    ply = minimum number of half-moves from the start position needed to reach it (0 = start). Even = White to move.
"n":    8 integers, games that VISITED this position, per rating band (index = bands[] order in manifest.json).
"eco":  ECO code if this exact position is the final position of a named line in lichess-org/chess-openings, else null.
"name": that opening name, else null (an unnamed position usually belongs to the nearest named ancestor on its path).
"path": space-separated SAN moves, White first, of the most common move order of length p that reaches the position
        (always replays legally from the start position; use it to show a move list and to rebuild a board).
"c":    only on ply-8 nodes that have deeper children: the chunk file name (relative to `dir` in the manifest).
```

**Edge** (one per parent position and move):

```
"f","t": ids of the position before and after the move.   "m": SAN.   "u": UCI.
"n":     8 ints, games (per band) in which this move was played in the parent position, whatever the move order that
         led to the parent (transpositions are merged).
"w","d": 8 ints each, of those games White won / drew. Black wins = n - w - d.  (Always White's point of view,
         whoever is to move.)  White score = (w + d/2) / n.
```

## Rules the data follow

* Nodes are positions, not move sequences, so transposed lines are one node with several incoming edges. A node's
  `n` is the sum over **all** visits, including those through edges that were pruned from the file, so
  `n >= sum(outgoing edge n)` always holds (per band); equality is rare because games end, are cut at 16 plies, or
  continue by a pruned move.
* Edges only go from ply `p` to ply `p+1` (`p` = minimum ply). A move that returns to an earlier position
  (e.g. `Nf3 Nf6 Ng1 Ng8`) is omitted, so the graph is acyclic and a tree view cannot loop. About 0.02 % of visits are such returns.
* Move popularity in band `b` at a node: `edge.n[b] / node.n[b]`. Show an arrow/percentage only if `node.n[b]` is large enough
  (we suggest at least 30 games in the selected band; the lowest bands have few games, see `bands[].games`).
  "All bands" is the element-wise sum.
* Pruning (total games over all bands): an edge leaving a node at ply <= {{EARLY_PLY}} (target plies 1 to 5) is kept if it has at
  least {{EARLY_FLOOR}} games; edges to plies 6 to 8 need at least `minCountCore` ({{CORE_MIN}}); edges to plies 9 to 16 need at least
  `minCountChunk` ({{CHUNK_MIN}}). Rarer moves are simply absent, and a kept node is only present if some kept edge leads to it.
* The same chunk file may be needed by several boundary nodes, and a position at ply >= 9 can appear in several chunk
  files (transposition across subtrees). When merging, key nodes by id and edges by (f, t, m): duplicates are identical.
* Rating band = average of White's and Black's rating at game time: `u900` below 900, `b900` 900-1099, `b1100`, `b1300`,
  `b1500`, `b1700`, `b1900`, `b2100` (2100 and above). These are Lichess (Glicko-2) ratings, which run higher than FIDE/USCF at the same strength;
  the top band is 2100+ online, not master play.
