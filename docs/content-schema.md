# Content schema v1 (the contract between content workers and the app)

Replaces v0. Authored files are JSON; **evidence is generated by `tools/validate.py` and never hand-edited.** IDs are permanent: never rename or reuse; deprecate and add. All text is **original wording**. Evidence labels in explanations are not allowed to overclaim (see "Explanations").

## Layout
```
content/skills/<SKILL>.json          skill nodes (depths, prerequisites)
content/items/<name>.json            {"positions":[...], "items":[...]}   (exercises with machine-checked claims)
content/lessons/<LESSON-ID>.json     lessons (cards, step-through boards, items, practice sets, contrasts)
content/_evidence/*.evidence.json    GENERATED by the validator
```
`tools/build_content.py` flattens all of it into `app/public/content/` for the app (manifest, skills, items with embedded positions, lessons, verified-status map).

## ID conventions (globally unique across all files)
- Positions `P-<AREA>-<n>` (generated: `PG-...`, puzzles: `PL-<lichessPuzzleId>`). Items `I-...` (generated `IG-...`, puzzle `IL-<id>`). Lessons `L-<SKILL>-<n>`. Families `FAM-...`.
- **Family** = a set of positions that are variations of one teaching situation (e.g. mirrored, colour-flipped, one pawn moved). **A family is never split between training and test**: the app uses family to avoid leakage. Give every position a `family`.

## Position
`{ "id", "fen", "family", "provenance": {"kind": "authored|generated|lichess_puzzle|lichess_game|public_domain_book", "ref": "...", "licence": "project|CC0|..."} }`
Every position must be a legal FEN (`is_valid()`), and no learner-facing "win" may be a dead draw (the validator checks this for material claims).

## Item (an exercise)
```
{ "id": "I-...", "skill": "TAC.FORK.D2",          // SKILL.DEPTH (depths D0..D5)
  "cue": 1|2|3|4,                                  // 1 named · 2 themed set · 3 mixed/unlabeled · 4 in play
  "task": "find_move|select_squares|predict_outcome|classify_position|threat_detection|play_out",
  "position": "P-...", "prompt": "...",
  "answer": { ... },                               // see below
  "claims": [ {id, type, params, statement?} ],    // at least one; every claim is machine-checked
  "tags": ["theme.fork", "node.TAC.FORK", "kind.puzzle", "tier.2"],
  "hints": ["attention cue", "relation cue", "partial line"],   // escalating; never the solution itself except last
  "explain": "One or two sentences of WHY, using only facts the claims verify.",
  "feedback_by_move": { "e2e4": "Why this plausible wrong move fails." },
  "contrast_group": "CG-...",                      // items that form a working / failing / irrelevant family
  "orientation": "white|black|auto",
  "difficulty_prior": {"scale":"lichess_puzzle","rating":1450,"rd":78,"plays":2300,"grade":"G1"},
  "source": {"kind":"lichess_puzzle","id":"abcde"},
  "review": {"status": "machine-only|needs-human|human-reviewed", "reviewer": null} }
```
**Answer shapes**
- `find_move`: `{"moves":["d5c7", ...]}`: the **accepted set**, all of which the validator must show are acceptable (use `best_move_in` or material/mate claims). Wrong-but-plausible moves go in `feedback_by_move`.
- `select_squares`: `{"from":"d4","squares":[...]}` (destinations of the piece on `from`) or `{"squares":[...]}` (e.g. "tap every attacked square").
- `predict_outcome`: `{"outcome":"yes|no|..."}` with optional `options`.
- `classify_position`: `{"class":"..."}` with required `options` (e.g. `["tactic","quiet","defend"]`).
- `threat_detection`: `{"threat_move":"h5f7"}`; the learner is shown the position and asked what the **opponent** threatens (the UI gives the opponent the move). Claims use `null_move_first`.
- `play_out`: `{"goal":"win|draw|hold","max_moves":40}`; played against the engine opponent from the position; claims establish that the goal is achievable (tablebase or engine).

## Claim types (all verified by `tools/validate.py`)
| type | params | meaning |
|---|---|---|
| `legal_move` / `illegal_move` | `move` | legality |
| `legal_destinations` | `from`, `to[]` | exact set of squares the piece can go to |
| `legal_moves_set` | `moves[]` | exact set of all legal moves |
| `game_state` | `state` (checkmate/stalemate/check/ongoing) | for the side to move |
| `mate_in` | `move`, `n`, optional `null_move_first` | forced mate (engine); `null_move_first` = "what does the opponent threaten?" |
| `material_after_move` | `move`, `min`/`max` | mover's net material change along the engine's best-defence line, measured at its last capture; a `min>0` claim fails if the result is a dead draw |
| `quiet_position` | `max` | no line wins more than `max` pawns for the mover (v0 heuristic) |
| `eval_range` | `min`, `max`, `depth?` | engine eval, **White's POV**, centipawns |
| `best_move_in` | `moves[]`, `within_cp?` | the engine's best move is in the set and every listed move is within `within_cp` (default 40) of best |
| `move_loses` | `move`, `cp` | the move is worse than the best move by at least `cp` |
| `attackers` | `square`, `color`, `count` | number of that colour's pieces attacking the square |
| `loose_pieces` | `color`, `squares[]` | exact set of that colour's non-king pieces that are attacked and undefended |
| `tablebase` | `result` (win/draw/loss for the mover), optional `move` | exact (≤7 pieces, Lichess service; cached) |

| `move_is_not_mate` | `move`, optional `null_move_first` | the move is legal and does not deliver checkmate (with `null_move_first`: legal for the opponent after the side to move passes) |
| structure claims | see "Structure claims" below | exact facts about pawns, files, squares and pieces, computed by `tools/structure.py`; no engine |

Modifiers (hardening round): `material_after_move`, `quiet_position` and `move_is_not_mate` accept `"null_move_first": true`: the side to move passes (refused if it is in check) and the claim is about what the OPPONENT could do, so "nothing is threatened" and "the opponent threatens to win the knight" can be machine-checked. The structure claims, `attackers` and `loose_pieces` accept `"after_move": "<uci>"`: the claim is evaluated on the position after that legal move ("the move puts the knight on an outpost"). `after_moves` (a list of UCI moves, played in order, each legal) does the same for a sequence such as a capture and its recapture. `legal_destinations` lists each square once (a promotion square is one destination, not four).

### Structure claims (exact, no engine; the code is `tools/structure.py`, differentially tested in `tools/selftest.py`)
Colours are `"white"`/`"black"`; squares are UCI names; "relative rank" counts from the colour's own back rank. Only pawns count as pawns; pins, en passant and promotion are ignored. Wherever a set is claimed (`squares`), the claim passes only if the computed set is EXACTLY equal; `includes` (subset) and `excludes` (disjoint) are accepted as weaker checks. Where a definition simplifies ordinary chess usage, the item text must not say more than the definition.

- **`pawn_set`** `{kind, color, squares}`. `passed`: no enemy pawn on the same or an adjacent file ahead of it (enemy pieces and kings are ignored). `isolated`: no own pawn on either adjacent file. `doubled`: every pawn on a file that holds two or more own pawns. `backward`: has an own pawn on an adjacent file, but every neighbouring own pawn is strictly ahead of it, and the square directly in front of it is attacked by an enemy pawn (a piece standing there is ignored). `connected`: an own pawn on an adjacent file at the same relative rank or one rank apart. `protected`: defended by an own pawn. `protected_passed`: passed and protected. `connected_passed`: passed with another passed own pawn on an adjacent file within one rank. `blockaded_passed`: passed, and the square in front holds an enemy non-pawn piece. `chain_base`: defends at least one own pawn and is defended by none. `hanging_pair`: two own pawns side by side on adjacent files and on their 4th or 5th relative rank, the only own pawns on those two files, with no own pawn on the file beyond either of them, and no enemy pawn on either of the two files. `majority_side`: wings are files a-d and e-h; on every wing where the colour has strictly more pawns than the opponent, all of its pawns on that wing are returned.
- **`pawn_islands`** `{color, count?, islands?}`: maximal runs of adjacent files holding at least one own pawn; `islands` lists them as file strings (`["ab","d","fgh"]`).
- **`open_files`** `{open?, half_open_white?, half_open_black?}`: exact lists of file letters. Open: no pawn of either colour on the file. Half-open for a colour: none of its own pawns but at least one enemy pawn on the file. Any subset of the three keys may be claimed; at least one is required.
- **`holes`** `{color, squares}`: squares on that colour's relative ranks 3-5 (ranks 3-5 for White, 6-4 for Black) with no own pawn on them that no own pawn attacks now and none can attack by advancing (no own pawn on an adjacent file at relative rank at most the square's rank minus one). Pieces on the square are ignored. A hole is a fact about the owner's pawns only.
- **`outposts`** `{color, occupied, squares}`: a square on relative ranks 4-6 (ranks 4-6 for White, 5-3 for Black) that an own pawn defends, that no enemy pawn attacks now and no enemy pawn can attack by advancing (no enemy pawn on an adjacent file at or beyond the attacking rank; pawn captures that change file are not considered), and on which no pawn of either colour stands. `occupied` is required and filters by what stands on the square: `any`, `empty`, `own` (an own non-pawn piece), `not_own` (no own piece, so empty or an enemy piece).
- **`bishop_pair`** `{holders}`: the exact list of colours that own at least one light-squared and at least one dark-squared bishop (`[]` when neither does).
- **`pawn_colours`** `{color, light?, dark?}`: the number of the colour's pawns on light squares and on dark squares (a1 is dark). Good-versus-bad bishop items compare these with the bishop's square colour.
- **`mobility`** `{square, mode, count}`: `legal` = the number of distinct squares the piece on `square` can legally move to, computed as if its colour were to move (so a pinned piece scores 0 and a piece in a position where its own king is in check is limited to answers to the check); `squares` = the number of squares it attacks that are not held by an own piece (pieces only; pins and checks ignored).
- **`king_pawn_shield`** `{color, squares}`: the colour's own pawns standing on the three files centred on its king's file, on the two ranks directly in front of the king (towards the enemy), wherever the king stands.
- **`space`** `{color, mode, count?, squares?}`: the number (and optionally the exact list) of squares in the OPPONENT's half (ranks 5-8 for White, 1-4 for Black) attacked by at least one own pawn (`pawn_attacks`), or attacked by an own pawn and by no enemy pawn (`pawn_controlled`). An optional `region` (a list of squares, e.g. `["d4","e4","d5","e5"]`) replaces the opponent's half. Occupancy is ignored. This is a counting rule, not a judgement that the space is useful.
- **`wing_pawns`** `{color, wing, count}`: the number of the colour's pawns on the queenside (files a-d) or the kingside (files e-h).
- **`pawn_attackers`** `{square, color, count}`: the number of pawns of that colour that attack the square (pieces do not count; use `attackers` for all pieces).
- **`piece_attacks`** `{square, squares}`: the exact set of squares the piece on `square` attacks (squares holding its own pieces are included, i.e. "defends"; pins and checks are ignored).
- **`rooks_connected`** `{color, value}`: whether two of the colour's rooks stand on one rank or file with no piece of either colour between them.
- **`piece_on`** `{square, piece}`: the piece symbol on the square (`"N"` white knight, `"b"` black bishop ...) or `"empty"`.
- **`king_wing`** `{color, wing}`: `queenside` (king on files a-c), `centre` (d-e) or `kingside` (f-h).
- **`moves_where`** `{property, moves}`: the EXACT set of legal moves that have the property, so an item may accept every such move and none else. Properties: `connects_rooks` (not connected before, connected after), `to_outpost` (a knight or bishop move whose destination is an outpost square for its colour after the move), `rook_to_open_file`, `rook_to_half_open_file` (half-open for the mover), `rook_to_seventh` (a rook arrives on its seventh relative rank from elsewhere), `blockades_passed` (a knight, bishop, rook or queen lands on the stop square of an enemy passed pawn), `pawn_move_attacks` (needs a `square`: a pawn move after which the moved pawn attacks that square).

Settings recorded for every check: engine, depth, hash, threads. Engine results are **evidence under recorded limits, not proofs** (see `docs/curriculum-map-v1.1.md`).

## Tags vocabulary (items)
`theme.<lichess theme>` · `node.<SKILL.ID>` (no depth) · `cue.<1-4>` · `tier.<0-7>` · `kind.<generated|puzzle|authored|quiet|game>` · `family.<FAM-...>` · `lang.en`. Lessons select practice items by tag intersection.

## Skill node (`content/skills/<SKILL>.json`)
`{"id":"TAC.FORK","title","strand":"S3","tier":2,"depths":{"D0":{"outcome":"...","prereqs":["..."]}, "D1":..., ...},"misconceptions":[...],"sources":["sources/sheets/..."]}` prereqs are `SKILL.Dn` strings. Hard prerequisites must form an acyclic graph.

## Lesson (`content/lessons/<ID>.json`)
```
{ "id":"L-TAC-FORK-1","title":"...","skill":"TAC.FORK","depth":"D1","minutes":8,"outcomes":["..."],
  "steps":[
   {"type":"card","text":"≤ 70 words, **bold** allowed, \n for line breaks"},
   {"type":"board","fen":"...","caption":"...","line":[{"move":"d5c7","say":"≤ 20 words"}],"arrows":[{"from":"d5","to":"c7"}],"highlight":["a6"],"claims":[...]},
   {"type":"item","item":"I-..."},
   {"type":"practice","tags":["theme.fork","cue.3"],"n":6},
   {"type":"contrast","title":"...","prompt":"Predict, then check.","working":"I-...","failing":"I-...","irrelevant":"I-..."},
   {"type":"reflect","kind":"confidence|expect|unsure","prompt":"..."}],
  "review":{"status":"needs-human"},"sources":["..."] }
```
Rules: no card without a board task within the next two steps; every `board.line` must be legal move by move; every `claims` entry is validated against that step's `fen`; no pin/fork/etc. claim about a position without a claim that checks it. Teach **conditions, not rules**, and give the failing look-alike (CD-4). Mark `review.status` honestly.

## Explanations
`explain` and `say` text may only assert what a claim establishes (e.g. "the knight attacks both the king and the queen" needs a `legal_move` + `material_after_move`; "the pawn on d6 defends e5" is a rules fact the validator can check via `legal_destinations`/`game_state`/attacker counts). Do not write evaluations like "White is winning" unless an `eval_range` or `tablebase` claim backs it. Avoid claiming **why** a strong player chose a move.

## Not in the schema yet
Acceptance sets for strategic plans (several valid plans), multi-defence tactic trees, progression within a family. Add when the first plan-choice items are authored.

## Lesson and item extensions the app supports (added after authors needed them)
- Step flags: `silent: true` on `item`, `practice` and `contrast` steps (no hints, no thinking prompts); `ask_confidence: true` shows the confidence chips even on items below cue 3 (self-calibration lessons).
- Reflect fields: `{id, label, options?}` as before; `type: "number"` shows a number box; with `answer` (and optional `tolerance`, default 0) the step says "Right" or shows the answer after saving. The answers are asserted by the authoring script, not by the validator (no claim type exists for arithmetic).
- Item `answer.options`: answer choices for predict_outcome and classify_position (the top-level `options` is also read). Item `answer.line` plus `answer.plies` with tag `mode.variation`: the learner enters the whole line, both sides. Item `display {study_seconds, hide[], reveal:'after_answer'}`: study the position, then pieces on `hide` squares vanish. `threat_move: "none"` or `outcome: "none"` on a threat_detection item means there is no threat.
- The Thinking Loop panel exists for LOOP.V1-V3 only (`app/src/lib/loop.ts`).
